# Architecture: Spring Boot + GraalVM + hono/html HDA demo

## Overview

A **Hypermedia-Driven Application (HDA)**: HTML is rendered server-side and the browser swaps in
fragments with htmx — no SPA, no client-side rendering.

- **Spring Boot 4.0.3** (Java 21) — Spring MVC controllers, `JdbcClient` persistence
- **hono/html** — TypeScript components written with hono's `html` tagged-template function,
  bundled by esbuild into a single `ssr.js`
- **GraalVM Polyglot 25.0.2** — runs `ssr.js` inside the JVM at request time. The `polyglot` / `js`
  artifacts are plain libraries (work on a stock JDK); a GraalVM JDK is used at runtime (see the
  `Dockerfile`) so GraalJS JIT-compiles hot JS instead of interpreting it. No native image.
- **htmx 4 + hyperscript** — browser-side partial updates

The templates are plain functions — `(vm: SomeModel): HtmlResult => html`…`` — not JSX. `String(...)`
on the result yields the HTML. There is no `hono/jsx`, no `renderToString`, no virtual DOM anywhere.

## Request pipeline

```
Browser  GET /
  → MainController.redirectRoot()                 → 302 redirect to /uiroute/Page

Browser  GET /uiroute/Page
  → PersonUIController.uiroute("Page")
      → JTSPersonRouteName.valueOf("Page")        [unknown name → 404 ResponseStatusException]
      → PeopleService.personTableModel()          [SQL → Java record]
      → new PersonPageModel(tableModel)           [assemble view model]
      → JsxRenderer.render(JTSPersonRouteName.Page, vm)
          → jsonMapper.writeValueAsString(vm)     [VM → JSON string]
          → pool.borrow()                         [acquire a GraalVM Context]
          → ctx.getEntryFunction("render")
               .execute("Page", vmJson)           [cross-language call]
              → render.ts: personRoutes["Page"].render(JSON.parse(vmJson))
              → String(Layout(html`… Page(vm) …`))  [hono/html → HTML string]
          → result.asString()
          → pool.release(ctx)
      → return String                             [Spring writes the HTTP response body]
```

**JSON is the only Java↔JS contract.** View models are serialized to a JSON string, passed across
the GraalVM boundary as a plain string, and `JSON.parse`'d in TypeScript. No GraalVM `Value`
proxying, no Java↔JS object bridging.

`PersonTable` is the one route that needs a `search` param instead of `id`, so it has its own
`@GetMapping("/uiroute/PersonTable")` method rather than growing `uiroute()`'s signature; Spring MVC
matches the literal path before the `{name}` template. The `uiroute()` switch's `default` branch
throws `IllegalStateException` for any route that has such a dedicated endpoint.

## GraalVM integration layer — `inbound/web/infra/js/`

| Class | Role |
|---|---|
| `JsHolder` | Owns one shared `Engine` (created at startup — lets GraalVM JIT hot JS across contexts). `buildSource()` reads `ssr.js` from `app.ssr.resource` and builds a `Source`; `buildPool()` creates the `SimplePool`. `initPool()` discards and rebuilds the pool on hot-reload. |
| `JsConnection` | One pool slot = one GraalVM `Context`. On construction: inject a `TextEncoder` polyfill (hono needs it, GraalVM doesn't provide it), inject `var module = {exports:{}}; var exports = module.exports;` for CommonJS, `eval` the whole `ssr.js`, then scan `module.exports` for callables into a `Map<String, Value>`. |
| `SimplePool<T>` | `ArrayBlockingQueue` sized to `availableProcessors()`. `borrow()` blocks until a slot frees — GraalVM `Context`s are **not** thread-safe. |
| `JsxRenderer` | The `@Service`. `render(JTSPersonRouteName route, Object vm)`: serialize `vm` to JSON, borrow a slot, `getEntryFunction("render").execute(route.name(), vmJson)`, `asString()`, release. |

## TypeScript layer — `inbound/web/*.ts`

esbuild bundles everything reachable from `render.ts` into one `target/classes/graaljs/ssr.js`
(`--bundle --platform=neutral --format=cjs`). `platform=neutral` keeps Node/browser globals out;
`format=cjs` matches the `module.exports` shim.

### Entry point — `render.ts`

```ts
export function render(route: string, vmJson: string): string {
  const routeDefinition = personRoutes[route];
  if (routeDefinition) return String(routeDefinition.render(JSON.parse(vmJson)));
  return String(html`<div>ROUTE '${route}' NOT FOUND</div>`);
}
```

It does **not** dispatch itself — it looks `route` up in `routes.ts`'s `personRoutes` map. `String(...)`
at this boundary is required: `html`…`` returns a boxed `HtmlEscapedString` (possibly a `Promise`),
and `JsxRenderer` calls `Value.asString()`, which needs a primitive string. `HtmlResult` everywhere
inside the components; stringify exactly once here.

| File | Role |
|---|---|

## Java → TS generation (Java is the source of truth)

Two `process-classes`-phase Maven plugins keep the TS side in sync; both outputs are git-ignored and
rebuilt on every `mvn package`.

1. **`cz.habarta.typescript-generator`** — scans `*Model` / `*VM` classes and the enums
   `JTSPersonRouteName`, `JTSPersonEventName`, and writes `generated/types/vm-types.d.ts`
   (`mapEnum: asUnion`, `outputFileType: declarationFile`). Types only, no runtime values.
2. **`org.codehaus.gmavenplus` inline Groovy script** (in `pom.xml`) — reflects over
   `HonoWebApiSharedConsts.HonoWebApiConsts` and writes `generated/types/web-api-consts.ts` with the
   two mutation path templates as **runtime** `const` strings (needed because `routes.ts` does
   `HonoWebApiConsts.PERSON.replace('{id}', id)`). Needs `gmavenplus-plugin` 5.1.0 +
   `org.apache.groovy:groovy` 5.1.1 on JDK 25.

So: add a route → add the `JTSPersonRouteName` enum value, wire `PersonUIController`, add the
`personRoutes` entry in `routes.ts` (the `satisfies` makes a missing entry a TS error).

## htmx / hyperscript choreography

- `hx-get` / `hx-put` / `hx-delete` on elements → partial swaps.
- Hyperscript `_="…"` attributes → client-side DOM events, no JS files.
- `<template hx-trigger="…">` — invisible htmx triggers embedded in rows, listening for custom events.

Event names come from `JTSPersonEventName` (`PERSON_UPDATED`, `PersonDetailsRow_CloseCmd`,
`PersonEditor_CloseRequested` — the last two `// TS-only`). `.ts` code never writes an event name as
a bare string; it calls `eventName('…')`, which typechecks against the generated union. Names use
`UPPER_SNAKE` / `Word_Word` — both safe to `send` unquoted in hyperscript (a hyphenated name is not).

**Saving an edit:**
1. Save button fires `PUT /person/{id}` with `hx-swap="none"`.
2. `PersonActionController` sets `HX-Trigger: {"PERSON_UPDATED": {"id": 5}}`.
3. htmx dispatches a `PERSON_UPDATED` DOM event `{id: 5}`.
4. A `<template hx-trigger="PERSON_UPDATED[detail.id === 5] …">` inside the row re-fetches the row.

`HTMXConsts.java` holds the response-header name constants.

## Dev hot-reload (`spring.profiles.active=dev`)

1. **`watch.ts`** (Bun) watches `src/main/java/**/*.ts` → runs esbuild → rewrites
   `target/classes/graaljs/ssr.js`.
2. **`JsBundleWatcher`** (`@Profile("dev")`, `@Scheduled(fixedDelay = 500)`) polls that file's
   `lastModified`; on change → `jsHolder.initPool()` (rebuild the Context pool) +
   `devReloadSSE.broadcastReload()`.
3. **`DevReloadSSE`** (`@Profile("dev")`, `SseEmitter` at `GET /dev-reload`) pushes a `reload` event;
   `static/js/dev.js` listens with `new EventSource("/dev-reload")` and calls `location.reload()`.

`spring-boot-devtools` is on the classpath but its LiveReload is disabled
(`spring.devtools.livereload.enabled=false`) in favour of the SSE mechanism above;
`spring.devtools.restart.exclude=graaljs/**` keeps a bundle rebuild from triggering a JVM restart.

## Persistence

- **HSQLDB** in-memory, **Flyway** migration `V1__create_person_table.sql`
  (`spring.sql.init.mode=never` — schema is Flyway's job).
- **`HSQLPeopleRepository`** uses Spring `JdbcClient` and returns typed Java records directly.
- **`DBInitializer`** (`@PostConstruct`) seeds 150 people with `net.datafaker.Faker` on `new Random(0)`
  — the Playwright suite relies on the deterministic first person ("Jackie Rau").

## Key design decisions

| Decision | Rationale |
|---|---|
| hono `html` tagged templates (not JSX) for SSR | Plain functions, no JSX toolchain/`jsxImportSource`, `String()` = HTML |
| JSON string as the only Java↔JS contract | Simple, debuggable, no GraalVM `Value` proxying |
| Blocking pool of GraalVM `Context`s | `Context` is not thread-safe |
| Java as the source of truth, TS generated | Route names, event names and VM shapes can't drift; a rename on the Java side is a TS compile error |
| `.ts` co-located with the Java web layer | Templates are the web tier, not a separate project |
| GraalVM as a library (GraalVM JDK only for JS JIT), no native image | Standard Maven build; the polyglot API works on any JVM |
| SSR bundle under `graaljs/`, not `static/` | Spring web-serves `static/**`; the bundle must not be publicly fetchable |
